## 2. B 应调用哪个入口

自然语言问题优先走：

```text
网页 → B /api/v1/ask 与路由 → C answer_sql → C 内部生成、校验、执行 → B 组织答案和展示
```

- C 负责 SQL 生成和执行，B 不必再重复生成一遍 SQL。
- `SQLExecutor.execute_sql` 是接收 SQL 的下层入口，仅在 B 已持有明确 SQL 请求等场景使用。
- `answer_sql` 返回 C 内部草案对象，不是正式的完整 `/api/v1/ask` 响应。
- 同一 Python 后端可导入调用；分开部署需要另外封装 HTTP/MCP 等适配，目前不提供可直接调用的新服务 URL。

## 3. 环境准备

从项目根目录运行，使用项目 `.venv` 或安装 `requirements-c.txt` 的等价 Python 环境。新后端进程需拥有以下环境变量：

| 环境变量 | 用途 |
|---|---|
| C_SQL_MODEL_ENDPOINT | 完整 HTTPS chat-completions 请求地址 |
| C_SQL_MODEL_NAME | 平台实际支持的模型 ID |
| C_SQL_MODEL_API_KEY | 通过后端安全配置提供的密钥 |

不会自动读取 `.env`。在一个 VS Code 终端里配置变量，不会自动传给另一个终端、已启动的 B 服务或调试进程；应在已配置的终端启动 B，或通过后端启动环境配置。不把密钥发送给前端或写入源码。

当前默认模型适配器是全局环境配置，不是按 `profile.model_profile` 动态选模型。真实调用有费用；`DemoJSONModel` 不调用 API。

## 4. 可运行的 Python 调用示例

以下示例可从项目根目录作为 Python 脚本运行。默认真实模型；先测试离线时将 `use_demo` 改为 `True`。示例不实现 B 的 HTTP 路由。

```python
import json
import uuid

from backend.sql_module import Registry, AccessContext
from backend.sql_module.generation import DemoJSONModel
from backend.sql_module.service import NLQueryService

registry = Registry.load()
use_demo = False
service = NLQueryService(
    registry,
    model=DemoJSONModel() if use_demo else None,
)

# 仅用于本地联调：允许读取 profile 配置允许的所有表。
# 正式 B 后端须根据已认证身份构造 AccessContext，不能信任前端自报权限。
access = AccessContext.local(registry)

request = {
    "request_id": "b-" + str(uuid.uuid4()),
    "profile_id": "chinook",
    "question": "客户数量是多少？",
    "context": {"metric_ids": ["customer_count"]},
    "options": {"max_rows": 50, "show_trace": True},
}
result = service.answer_sql(request, access)
print(json.dumps(result, ensure_ascii=False, indent=2))
```

预期 `status=answered`，`sql_results[0].rows=[{"customer_count":59}]`，`query_artifacts` 包含 SQL。离线模式会在 limitations 中标注固定问法演示。

注意：这里只能将 `customer_count` 用于“Customer 全部记录数”的演示指标。它不是“某季度购买客户数”，不能给所有问题都附上这个指标。当前目录未完整注册销售指标。

## 5. 请求格式与 B 的转换责任

必填：`request_id`、`profile_id`、`question`。可选：`context`、`options`。未知字段会被拒绝。

| 字段 | 实际支持 |
|---|---|
| options.max_rows | 1—200，默认 50 |
| options.show_trace | 布尔值，默认 true |
| context.metric_ids | 当前 profile 已注册的指标 ID；未知指标会报错 |
| context.business_context | `[{"ref_id":"来源标识","text":"经确认的口径或资料"}]`，最多 20 项 |
| context.resolved_slots | 只能传 profile.slots 已声明、类型与取值合法的槽位 |
| context.reference_time | 带时区的 ISO 8601 时间；不等于已实现相对时间解析 |

B 不能将网页请求原样传给 C：`session_id`、`user_role` 和 `options.top_k` 等属于上层，不在 C 此入口的允许字段中。B 保留会话，构造所需 C 请求；权限通过服务端 `access` 参数传递。

业务上下文可以传定义和规则，但不得在评测时把标准答案作为上下文。C 接收到资料并不保证模型完全遵守，仍需结果验证。

## 6. 返回字段如何展示

| C 返回字段 | B 使用方式 |
|---|---|
| sql_results[].columns、rows | 生成表格；每个结果独立展示，不把多次查询混成一张表 |
| sql_results[].row_count、truncated | 展示已返回行数；截断时提示结果不完整 |
| sql_results[].source | 展示数据库名称和表来源 |
| query_artifacts[].sql、params | 按 query_id 与查询结果关联，展示参数化 SQL 与参数，勿字符串拼接后重新执行 |
| query_artifacts[].schema_version、metric_refs | 展示结构和指标版本依据 |
| metric_definitions、limitations | 展示已引用定义和限制，不隐去关键不确定性 |
| trace | 显示工具状态与耗时，不是模型隐性思维链 |
| error | 展示结构化失败信息，不把错误呈现为零销售额 |

数字可用于图表，但图表选择由 B 实现，目前 C 不生成图表配置。对 Decimal 字符串按金额规则转换和展示，不能把 null 强制转成 0；不要为作图改变日期、ID 或金额含义。

`show_trace=false` 目前只关闭详细 trace，成功结果仍包含 query_artifacts。若产品需要隐藏 SQL 或参数，B 需要按展示权限过滤，不能只依赖这个选项。

## 7. 状态与正式响应的映射

- `answered`：获准 SQL 已执行并返回；不是语义已核验正确。空结果也可能 answered，聚合无匹配可能是一行 null/0。
- `error`：检查 error.code 与 details.reason；可能来自模型网络/超时、输出格式、SQL 候选或数据库。
- `unsupported`：当前能力明确不支持，应保留限制/错误信息。
- 当前没有完整的自动澄清流程。缺必要槽位时可能返回 `error/MISSING_REQUIRED_SLOT`，clarification 仍为空；不要假设 C 已返回可直接展示的追问选项。

B 负责正式响应的 session_id、route、answer、intent、entities、time_range、documents、calculations 等。SQL 路径通常由 B 标记 route=sql；unsupported 必须按正式契约处理。C 的 `query_artifacts` 不在正式 v0.3 顶层字段中：可先由后端保留用于联调，需要对前端公开时与 A 确认兼容扩展，不擅自改变 sql_results 的既有结构。

请求错误、业务状态与 HTTP 状态要按照正式契约分类，不能所有 `status=error` 都机械映射为同一种 HTTP 状态。Registry.load 的配置异常可能在调用服务前抛出，B 启动时应处理。

## 8. 已有 SQL 的直接调用

```python
from backend.sql_module import Registry, AccessContext
from backend.sql_module.execution import SQLExecutor

registry = Registry.load()
result = SQLExecutor(registry).execute_sql({
    "query_id": "b-sql-001",
    "profile_id": "chinook",
    "sql": "SELECT COUNT(*) AS customer_count FROM Customer WHERE Country=:country",
    "params": {"country": "USA"},
    "max_rows": 50,
    "timeout_ms": 5000,
}, AccessContext.local(registry))
# 预期 success，customer_count 为 13；无需模型 API。
```

这里返回单个 v0.3 SQL 结果对象，状态为 success/rejected/failed，与 answer_sql 的外层状态不同。该输出不自带 SQL 字段，B 需保留对应请求。

## 9. 联调顺序与执行注意事项

1. 先用 DemoJSONModel 跑客户数量，验证 B → C → 表格/SQL 展示；页面标注离线演示。
2. 切换默认真实模型，运行同一题及未预设的问法，核对 59、美国客户 13；确认环境变量由 B 进程读取。
3. 验证错误场景的页面反馈：缺配置、超时、服务失败、生成不合法 SQL；不要静默切到固定答案。
4. 运行业务题集并逐题核对，保留限制和失败信息。不能把现有 6/10 执行成功当作 60% 答案正确。
5. AdventureWorks 和跨源题作为后续实库/联合验收项。

answer_sql 为阻塞式同步函数。如 B 使用异步 Web 框架，应使用受控线程池等方式调用，避免阻塞事件循环；并发承载与服务取消行为尚未验收。当前模型预算约 20 秒、总请求预算约 60 秒，但不是进程级硬截止，外层超时不保证内部立即取消，需在联调中确认。

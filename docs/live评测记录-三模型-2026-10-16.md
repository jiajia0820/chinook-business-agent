耗时结构：三轮的 111 s 答题时间里，**90.5 s 全部来自 `special-formula-005` 一题**
（两次模型尝试 37.0 s + 29.0 s，加上 8 s / 16 s 退避），另外 8.1 s 来自 `special-clarify-002`、
8.3 s 来自 `robust-012`。其余 116 题合计仅约 4.1 s，p50 32 ms，与 MiMo 基线同量级——
因为 45 次 `controlled_fallback` + 2 次 `controlled_business_query` 覆盖了绝大多数 SQL 类问题，
这些路径根本不调模型。

墙钟从基线 43.1 s 涨到 120.5 s（+77.4 s），答题累计从 25.0 s 涨到 111.0 s（+86.0 s），
增量全部落在上述三题的模型等待上；`boot_ms` 这三轮反而比基线快 2.4 s。
三轮均满足「墙钟 ≈ 启动 + 答题累计 + 约 1.9 s 评分写盘开销」（7.6 + 111.0 + 1.9 = 120.5），
基线那轮同样算法余 8.1 s，两个增量口径的差额（77.4 vs 86.0）就出在这块开销上，
与系统性能无关。

## 5. 超时定性：客户端截止截断，不是模型延迟差异

最直接的证据是三个不同模型的耗时几乎逐毫秒相同：

| 尝试 | DeepSeek | glm | Qwen |
|---|---|---|---|
| clarify-002 | 8062 ms | 8063 ms | 8063 ms |
| formula-005 第 1 次 | 37046 ms | 37078 ms | 37031 ms |
| formula-005 第 2 次 | 29031 ms | 29047 ms | 29047 ms |
| robust-012 | 8031 ms | 8063 ms | 8031 ms |

三个互不相关的模型不可能有毫秒级一致的响应时间。这些数字是我们自己的预算边界：

- 澄清 / 语义路由路径只给模型 **8 s**，到点即 `MODEL_TIMEOUT`。这个 8 s 是硬编码的
  `SEMANTIC_ROUTE_SECONDS = 8`
  （`services/agent_api/app/agent/graph.py:31`，第 250 行据此设 deadline）；
- 公式路径按 `backend/sql_module/service.py` 的 `MODEL_CALL_SECONDS = 45`（单次上限）、
  `MODEL_TOTAL_SECONDS = 100`（整轮上限）、`ANSWER_BUDGET_SECONDS = 115`（整答上限）控制：
  两次尝试分别在 37.0 s、29.0 s 被判超时，中间退避 8 s / 16 s，
  模型阶段合计 37 + 8 + 29 + 16 = 90 s，随后转受控查询计划。
  注意单次实际截断点（37 s / 29 s）都早于 45 s 上限，说明是网关侧连接先到期，
  而不是我们这边把 45 s 用完；这一点从常量本身推不出来，属于待查项。
- `backend/sql_module/generation.py` 的 `HTTPJSONModel.generate_json` 用
  `timeout=min(60, deadline-now)` 发请求，socket 超时或超过 deadline 都抛 `MODEL_TIMEOUT`。

结论：模型在预算内**一个字节都没返回**，属于「渠道无响应 / 响应远慢于预算」，
不是模型给出了错误答案。

## 6. 网关直连探针（独立诊断，未重跑任何失分题）

为区分「渠道挂了」和「模型太慢」，用 `tmp/probe_models.py` 对同一 endpoint、同一 Key
发最小请求（`say OK`，`max_tokens=16`），每个模型两次，客户端超时放宽到 120 s。
原始输出：`tmp/probe-models-20261016.log`（15:29–15:36）。

`GET /v1/models` 正常返回 15 个 id，含 `DeepSeek-V4.1-Flash`、`glm-5.3-flash`、
`Qwen3.8-Flash-Next`、`MiMo-V2.6-Flash`，说明 Key 有效、模型 id 无拼写问题。

| 模型 | 第 1 次 | 第 2 次 | 定性 |
|---|---|---|---|
| `MiMo-V2.6-Flash`（对照） | 200，12.94 s | 200，27.22 s | 可用，但最小请求也要 13–27 s，已超出语义路由的 8 s 预算 |
| `DeepSeek-V4.1-Flash` | **500**，3.48 s，`get_channel_failed`：「分组 auto 下模型 DeepSeek-V4.1-Flash 的可用渠道不存在（retry）」 | 200，3.59 s（上游自报 `deepseek-flash`） | 渠道不稳定：时有时无；命中时最快 |
| `glm-5.3-flash` | 读超时，120.05 s | 读超时，120.05 s | **渠道挂起**，120 s 内无任何 HTTP 响应 |
| `Qwen3.8-Flash-Next` | 200，15.58 s | 读超时，120.05 s | 极不稳定，一次 15.6 s、一次直接挂死 |

补充观察：三个模型的成功响应里 `content` 为空或极短、`reasoning_content` 有内容，
说明是推理型模型，`max_tokens=16` 全被思考吃掉。评测里的真实 prompt 带 schema、
指标定义和输出契约，比 `say OK` 大得多，推理时间只会更长——这与「8 s 预算内必然拿不到结果」一致。

综合判断：

1. **不是代码回归。** 三轮 `code_sha256`、`scorer_sha256`、`dataset_sha256`、`data_sha256`
   与 MiMo 基线逐字节相同，只换了模型。
2. **主因在供应商侧。** `glm-5.3-flash` 渠道挂起；`DeepSeek-V4.1-Flash` 在 `auto` 分组下
   间歇性没有可用渠道；`Qwen3.8-Flash-Next` 一半概率挂死。三者都无法稳定在 8 s / 45 s 预算内返回。
3. **次因是延迟方差大、预算偏紧。** 对照模型 MiMo 在评测里三次调用的实测值是
   3609 ms（成功，语义路由 8 s 预算内）、7891 ms（成功，公式路径 45 s 预算内）、
   8047 ms（超时，语义路由）；而 25 分钟后的探针对同一个 MiMo 发最小请求却要 13–27 s。
   同一个模型的响应时间在 3.6 s 到 27 s 之间摆动，说明当前 8 s 的语义路由预算
   对这一批推理型 flash 模型整体偏紧——MiMo 拿到 118/119 有相当成分是运气，
   它在 `robust-012` 上同样超时，且同一份代码在当天上午那轮（`db9900d`）里
   `robust-012` 又能 2109 ms 成功。

## 7. 这三轮成绩该怎么读

116/119 **不是这三个模型的答题能力**。三轮里模型成功返回 0 次，所以这实际上是
一次「模型完全不可用」的消融基线：它衡量的是受控查询计划 + RAG + 澄清策略在模型缺位时
能把系统托到什么程度——答案是严格口径 116/119、业务口径 119/119，
失分全部来自审计对「外部未完成」的保守判定，没有一题是业务答错。

与 MiMo 基线的 2 题差距（`special-clarify-002`、`special-formula-005`）恰好等于
MiMo 那轮唯一两次成功的模型调用。换句话说，**在 119 个评分单位里，只有 3 个单位的
严格 live 通过依赖模型真实返回**，其余 116 个单位由本地受控路径决定。

要真正比较这三个模型与 MiMo 的能力差异，需要供应商渠道恢复稳定后重跑；
按用户要求，本轮不重跑失分题，也不把不同轮次的最好成绩拼接成一个总分。

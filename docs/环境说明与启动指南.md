# 环境说明与启动指南（队友交接）

最后核对：2026-10-09，分支 `codex/chinook-complete`。

本文所有命令、端口、版本号、耗时和返回结果都在本机实测过，未实测的部分在第 11 节明确标注。

## 0. 最短路径

环境已经装好的人，只需要两个终端：

```powershell
# 终端 1，仓库根目录
uv run uvicorn services.agent_api.app.main:app --host 127.0.0.1 --port 8000
```

```powershell
# 终端 2，services/web 目录
cd services\web
npm run dev
```

然后浏览器打开 <http://localhost:5173>。

关闭：两个终端各按一次 `Ctrl+C`。

## 1. 需要装什么

| 组件 | 版本要求 | 本机实测 | 用途 |

- 不需要安装任何数据库服务。Chinook 是随仓库携带的 SQLite 文件 `data/chinook/Chinook.db`（1,007,616 字节），后端直接读文件。

- 不需要 Docker、Redis、消息队列。

## 2. 首次准备（每台机器只做一次）

```powershell
# 1) Python 依赖（仓库根目录）。走阿里云镜像，见 pyproject.toml 的 [[tool.uv.index]]
uv sync

# 2) 前端依赖
cd services\web
npm ci
cd ..\..

# 3) 配置文件
Copy-Item .env.example .env
```

然后编辑 `.env`，**必须改这一项**：

```dotenv
AGENT_MODEL_MODE=live
```

`.env.example` 里默认写的是 `offline`。留着 `offline` 的话服务能正常启动、网页也能正常打开，但走的是固定问答替身，不是真实模型生成的 SQL——这是最容易踩、而且不容易被发现的坑。判断方法见第 4 节。

再填三项模型配置（值向队长索取，不要提交进 Git，`.gitignore` 已命中 `.env`）：

```dotenv
LLM_API_KEY=<key>
LLM_BASE_URL=<openai 兼容地址>
LLM_MODEL=<模型名>
```

本机 `.env` 当前的非敏感项：`AGENT_MODEL_MODE=live`、`AGENT_BACKEND_MODE=offline_sql_d12`、`AGENT_ENABLED_PROFILES=chinook-music`、`AGENT_SQL_TIMEOUT_MS=180000`、`CORS_ALLOWED_ORIGINS=http://localhost:5173`。

### 哪些东西在 Git 里，哪些不在

**在库内、克隆即有、不需要额外下载或构建**：`data/chinook/Chinook.db`、`data/knowledge/` 的 D01-D12 与 `source-manifest.json`、`profiles/chinook/` 的 profile 与指标、`third_party/chinook_c/` 冻结快照、`backend/sql_module/` 的 C canonical 代码。

知识索引（909 chunks）**不是**库内产物，它在后端启动时由 `services/agent_api/app/knowledge/` 的代码从上述原始文件现场构建，所以克隆后不需要跑任何索引生成命令。

**不在库内、需要各自准备**：

- `.env` — 每人自行填密钥，已被 `.gitignore` 命中
- `.venv` — `uv sync` 生成
- `services/web/node_modules` — `npm ci` 生成
- `services/web/dist` — `npm run build` 生成，当前开发流程用不到
- `tmp/` — 评测与实验的本地产物，用 `scripts/run_agent_eval.py` 等脚本重新生成

## 3. 端口与进程

| 端口 | 进程 | 说明 |
|---|---|---|
| 8000 | uvicorn（后端 API） | 必须在**仓库根目录**启动，模块路径是 `services.agent_api.app.main:app` |
| 5173 | Vite dev server（前端） | 必须在 `services/web` 目录启动 |
| 4173 | `vite preview` | 配置里有，当前流程用不到 |

前端不直连 8000。`services/web/vite.config.ts` 把 `/api` 代理到 `http://127.0.0.1:8000`，代理超时 240 秒。所以：

- 两个端口都必须起来，缺一个网页就是空的或报错。
- 前端代码里请求的是相对路径 `/api/v1/ask`，不含主机名，因此 `localhost` 和 `127.0.0.1` 两种写法都能用（本机四个地址组合均实测 200）。
- `strictPort: true`，端口被占用时 Vite 会**直接失败**，不会自动换端口。

## 4. 怎么确认真的起来了

**第一步，探活。** 浏览器或命令访问 <http://127.0.0.1:8000/health>，期望：

```json
{"status":"ok","service":"agent-api","model_mode":"live"}
```

`model_mode` 必须是 `live`。如果是 `offline`，说明 `.env` 没生效或没改，回到第 2 节。

注意 `/health` 返回 200 **不代表**后端真的可用：配置或数据文件出问题时它照样返回 200，只是提问会拿到 503 `PROFILE_UNAVAILABLE`。所以还要做第二步。

**第二步，冒烟提问。**

```powershell
$body = @{ question = '2025 年 Rock 音乐销售额是多少？'; profile_id = 'chinook-music'; session_id = 'smoke-1' } | ConvertTo-Json -Compress
Invoke-WebRequest -Uri 'http://127.0.0.1:5173/api/v1/ask' -Method POST -Body $body `
  -ContentType 'application/json' -Headers @{ 'X-Request-ID' = 'smoke-001' } -UseBasicParsing -TimeoutSec 240
```

2026-10-09 实测结果：HTTP 200，`status=answered`，`route=sql`，答案含"销售额 174.24 USD"，耗时约 7-10 秒。走的是 5173 代理，所以这一条命令同时验证了后端、前端代理和真实模型链路。

响应顶层字段：`request_id, session_id, profile_id, status, answer, route, intent, entities, time_range, sql_results, documents, calculations, metric_definitions, limitations, clarification, trace, error`。

**第三步（可选），网页。** 打开 <http://localhost:5173>，问同一个问题，应看到答案、SQL、证据和执行轨迹。

补充：`docs/验收记录-2026-10-08.md` 记录当天 live 模型被供应商返回 401，所以那时 live 冒烟是失败的。**该问题现已解决**，本次实测 live 链路真实返回了答案。

## 5. 运行时依赖哪些文件

后端启动和提问会读取以下文件。按"改动的后果"分三档：

**A 档：缺任何一个，启动即 503 `PROFILE_UNAVAILABLE`**

- `data/chinook/Chinook.db` — Chinook SQLite 库
- `profiles/chinook/profile.json` — 数据源 profile
- `profiles/chinook/metrics.json` — 13 个指标口径

这三个是"canonical"路径的必需文件，代码只做存在性检查，不校验哈希，所以内容可以改（改完重启生效）。

**B 档：逐文件 SHA-256 + 字节数锁定，改了必须同步 manifest**

- `data/knowledge/D01`~`D12`（PDF / DOCX / PNG / Markdown 共 12 份）
- `data/knowledge/source-manifest.json`

后端按 manifest 里的 `sha256` 和 `size_bytes` 逐个校验原始字节，任何一份对不上就报 `KNOWLEDGE_SNAPSHOT_INVALID` / `PROFILE_UNAVAILABLE`，**不会**静默跳过。D12 更严格，`services/agent_api/app/knowledge/d12.py` 里硬编码校验它的 sha256、字节数 10949、标题"经营查询与数据使用 FAQ"、版本 V1.0、文档号 CHN-FAQ-12、生效日期 2025-07-01。

**这意味着负责业务文档的队友不能直接编辑 D01-D12。**要改内容，必须同时更新 manifest 里对应记录，D12 还要改 `d12.py` 里的常量。改完用第 8 节的两条命令验证。

另外 `.gitattributes` 现在第一行是 `* text=auto eol=lf`：仓库内所有文本文件统一按 LF 存储，检出时也不再受各机器 `core.autocrlf` 影响（本机系统级配置是 `true`），队友 clone 出来的字节与仓库 blob 完全一致。下面几条 `-text` 规则按“最后匹配优先”覆盖它，让 `third_party/chinook_c/**`、D12、`services/web/src/contracts/generated/**` 保持逐字节原样。**这两类规则都不要删**，否则在 `core.autocrlf=true` 的机器上 clone 会改写字节，哈希立刻失配。

D12 的 canonical 字节自 2026-10-09 起固定为 **LF / 10949 字节**，sha256 `939adb9abd7ed425a682edd356292ce70141a93abd1632ab6ca3b064d5105a7e`，manifest 与 `d12.py` 都以这个值为准。**不要用编辑器打开再保存 D12**：Windows 下多数编辑器会重存成 CRLF，字节数变 11095，哈希当场失配。这个坑真实发生过，而且方向相反：修复前仓库 blob 是 LF，manifest 锁的却是本机工作区的 CRLF 字节（11095），任何全新 clone 都会 `KNOWLEDGE_SNAPSHOT_INVALID`、后端启动即 503。修复提交是 `6b6664f`，已在真实全新克隆上验证通过，见第 11 节。

**C 档：冻结快照，禁止修改**

- `third_party/chinook_c/**` — C 首版隔离交付，19 个文件逐字节冻结

被 `artifact-manifest.json` 加代码里的 `ARCHIVE_SHA256`、`DATABASE_SHA256`、`SERVICE_SHA256` 三个常量锁死。详见第 6 节。

## 6. 两份 C 代码的区别（最容易搞错的一点）

仓库里有两份长得几乎一样的 C 模块，只有一份是活的：

| | 仓库根 `backend/sql_module/` | `third_party/chinook_c/backend/sql_module/` |
|---|---|---|
| 启动时是否加载 | **是** | 否 |
| 哈希校验 | 无，只查文件存在 | 有，逐文件 SHA-256 |
| 改了会怎样 | 重启后端即生效 | 触发 `PROFILE_UNAVAILABLE` |
| 谁在用 | `create_canonical_sql_integration` → 正式服务 | 部分测试的非 canonical 路径 |

调用链是：`backend_lifecycle.create_default_backend` → `sql_d12.create_canonical_knowledge_integration` → `c_offline.create_canonical_sql_integration`，其中 `root = PROJECT_ROOT`（仓库根），并以 `canonical=True` 导入 `backend.sql_module.*`。

配套的 profile 也是两份且内容不同：根目录 `profiles/chinook/metrics.json` 是 5,531 字节（13 个指标，活的那份），vendor 里的同名文件只有 413 字节。别改错目录。

两份 `Chinook.db` 内容一致，实测 SHA-256 均为 `adb73b5b0ea57598926fa8a72ffb2848c64f7f17a4e57b5e0c04a182e24f565c`，与代码常量相符。

## 7. 环境变量

| 变量 | 本机当前值 | 作用 |
|---|---|---|
| `LLM_API_KEY` | 已设置 | 模型密钥，不进 Git |
| `LLM_BASE_URL` | 已设置 | OpenAI 兼容地址 |
| `LLM_MODEL` | 已设置 | 模型名 |
| `AGENT_MODEL_MODE` | `live` | `live` 真实模型 / `offline` 固定问答替身。**演示必须是 live** |
| `AGENT_BACKEND_MODE` | `offline_sql_d12` | 后端形态，目前只支持这个值和 `unavailable` |
| `AGENT_ENABLED_PROFILES` | `chinook-music` | 只能是这个值，改了启动报错 |
| `AGENT_SQL_WORKERS` | `2` | SQL 执行线程数，上限 16 |
| `AGENT_MAX_INFLIGHT_REQUESTS` | `8` | 并发上限，超出返回 `CAPACITY_EXCEEDED`，上限 64 |
| `AGENT_SQL_TIMEOUT_MS` | `180000` | SQL 单轮预算。代码默认 60000，但 C 的整轮预算（模型重试 + 受控降级）约 115 秒，调小会在降级前被切断 |
| `AGENT_RAG_TIMEOUT_MS` | `5000` | 文档检索超时 |
| `AGENT_STARTUP_TIMEOUT_SECONDS` | `30` | 启动超时，上限 30 |
| `AGENT_SHUTDOWN_GRACE_SECONDS` | `10` | 关闭宽限 |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173` | 仅在绕过 Vite 代理直连 8000 时才起作用；正常流程走同源代理，不受影响 |
| `ADVENTUREWORKS_DATABASE_URL` | 空 | 留空即只用 Chinook。当前 `psycopg` 未安装，填了也用不了 |

`.env` 的加载由 `services/agent_api/app/main.py` 的 `load_runtime_environment()` 完成，会找仓库根的 `.env`。`uv run` 不会自动导出 `.env`，所以这步是代码自己做的——不要因为"看起来没 source 环境变量"就手工去 export。

### 不要用 `uv run pytest`

`pytest` 既不在 `pyproject.toml` 的依赖里，也不在 `.venv` 里（test extra 只声明了 `httpx`）。本机 `uv run pytest` 会落到全局的 `D:\py\Scripts\pytest.exe`，那个解释器没有 `sqlalchemy`，收集阶段就报：

```text
backend\sql_module\schema.py:3: in <module>
    from sqlalchemy import inspect
E   ModuleNotFoundError: No module named 'sqlalchemy'
```

这不是环境坏了，是用错了命令。后端测试统一用上面那条 `unittest discover`。

## 9. 常见故障

| 症状 | 原因 | 处理 |
|---|---|---|
| `[Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)` | 8000 已被占用，通常是上次的后端没关 | 关掉旧进程；`Get-NetTCPConnection -LocalPort 8000` 可查占用者 |
| Vite 启动即退出，提示端口被占 | `strictPort: true`，5173 被占不会换端口 | 同上，查 5173 |
| `/health` 返回 `model_mode: offline` | `.env` 里 `AGENT_MODEL_MODE` 不是 live，或 `.env` 不在仓库根 | 改 `.env`，重启后端 |
| 提问返回 503 `PROFILE_UNAVAILABLE` | A 档文件缺失、B 档哈希失配、或改了 `third_party/chinook_c/` | 看响应 `details.reason`；跑第 8 节两条知识校验命令定位 |
| 提问返回 `KNOWLEDGE_SNAPSHOT_INVALID` | 改了 D01-D12 但没同步 manifest，或 `.gitattributes` 的 `-text` 被删导致 CRLF 改写 | 恢复文件或重建 manifest |
| 全新 clone 直接报 `KNOWLEDGE_SNAPSHOT_INVALID`，提示 D12 hash or size mismatch | `6b6664f` 之前的历史问题：manifest 锁 CRLF 字节（11095），仓库 blob 是 LF（10949） | 拉最新 main 即可；若仍重现，先确认没被编辑器把 D12 重存成 CRLF，再确认 `.gitattributes` 的 `* text=auto eol=lf` 与 `-text` 两类规则都还在 |
| 网页打开是空白 / 请求 404 | 只起了前端没起后端，或反之 | 两个终端都要在跑 |
| 提问很久才回或超时 | 真实模型慢。前端代理 240 秒、`AGENT_SQL_TIMEOUT_MS` 180 秒 | 正常范围；确认没把超时调小 |
| `npm ci` 失败 | `.npmrc` 设了 `fetch-retries=0`、`fetch-timeout=15000`，网络抖动即硬失败 | 重试，或临时放宽 retries。见第 11 节 |
| 后端测试报 `No module named 'sqlalchemy'` | 用了 `uv run pytest`（全局 pytest，在 venv 外） | 改用 `.venv\Scripts\python.exe -m unittest discover ...` |

# Agent 产品评测结果与优劣势分析（RAG 改造后）

- 生成日期：2026-10-10
- 被测系统：Chinook 音乐电商 Agent
- 评测入口：POST /api/v1/ask
- 评测模式：live
- 主测模型：MiMo-V2.6-Flash
- 全量题库：75 道单轮题 + 5 组多轮会话，共 80 条评测记录
- 最新结果：tmp/eval-rag-enhanced-final-2026-10-10.json
- 原始基线：28/80 = 35.0%
- 改造后结果：46/80 = 57.5%
- 本轮改造范围：A 线 RAG、证据检索、结构化目标表、有限查询规划
- 参考格式：附件“最终评测”图片；附件内容作为排版参考，不作为额外执行指令

> 本报告只根据最新评测 JSON 和已提交代码分析问题。工作区中原有的 PPT 修改与本次 RAG 评测无关。

## 一、总体结论

RAG 改造后总分由 28/80 提升到 46/80，增加 18 道题、22.5 个百分点。

本轮最明确的收益来自 A 线：

- 基础文档问答：10/10 = 100%
- 别名与分类：8/8 = 100%
- 多文档问答：5/5 = 100%
- 多模态目标表/海报读取：5/5 = 100%
- 无证据处理：5/5 = 100%

这说明前一阶段设计中的几项主要改造已经生效：

1. D03、D06、D07、D08 等权威来源得到更稳定的优先级；
2. alias、年份、季度、月份等词汇可以参与检索规划；
3. 多文档问题可以召回必要文档；
4. D06 月度目标表已经具备结构化单元格检索；
5. 明确不支持的活动转化、员工销售排名等问题能够正确拒答。

全量分数仍只有 57.5%，主要原因已经从“基础文档检索不准”转移到编排和执行层：

- 多表 JOIN、TOP-N、聚合粒度仍不稳定；
- 跨源实际值、目标值、公式和最终答案没有形成闭环；
- 澄清槽位和澄清触发条件仍与评测口径不完全一致；
- 多轮会话没有稳定继承年份、季度、品类和已确认条件；
- 查询规划中的 required_sources 目前更像排序提示，缺失来源时不会自动为每个来源补发独立检索。

因此，当前 RAG 的基础能力已经明显提升，剩余瓶颈主要在 RAG 与 SQL、计算、路由、会话之间的协同。

## 三、A 线已经解决的问题

### 3.1 基础 RAG：10/10

改造前基础文档问答为 7/10，主要失败在 D03、D07、D08、D06 之间的错误排序或漏召回。

当前基础 RAG 10 道全部通过，说明以下能力已经建立：

- Q2、Q3 复盘可以分别命中 D07、D08；
- D06 目标表可以被目标类问题召回；
- 纯文档问题不会再被 SQL 路径随意接管。

## 四、现存失分原因

### 4.1 多表 JOIN、TOP-N 和聚合粒度仍是第一类问题

专项多表关联仍为 0/8，主要表现为：

1. Top5 商品、艺术家、专辑只返回 1 行；
2. 播放列表和客户金额排名被误送 RAG；
3. 支持负责人分布只返回 1 行，期望 3 行；
4. 分类订单数与购买客户数内容虽然接近正确，但行序不符合金标准；
5. 音频和视频混合订单题仍报 MISSING_REQUIRED_SLOT；
6. 基础 NL2SQL 的账单国家排名返回 10 行，期望 5 行。

这类问题不是当前 A 线检索失败，而是 SQL 生成和结果校验问题：

- SQL 没有稳定生成 ORDER BY ... LIMIT N；
- 多表 JOIN 后的聚合粒度没有被强约束；
- 查询需要的分组列、排序列和限制数量没有形成结构化中间表示；
- 结果验证只检查“有结果”，没有充分检查结果行数、排序方向和目标粒度；
- 某些查数外形问题仍然被误判为 RAG。

这部分直接影响基础 NL2SQL、多表关联、跨源客户分层、海报商品销售和多源排名题。责任主要属于 B 线 SQL 与 C 线路由，A 线只能提供文档口径和实体边界。

### 4.2 公式计算和跨源答案没有形成闭环

公式专项只有 1/6，跨源问答只有 1/10。

典型失败包括：

- 实际销售额和目标值都已可获得，但 gap、rate 没进入最终答案；
- Q2/Q3 实际值可以查询，但增长额和增长率未稳定输出；
- 客单价题被送到 SQL 后报缺少条件；
- Rock 销量达成率题没有形成 actual、target、formula 三类证据；
- 月度实际与目标题没有在答案中同时保留数据库值、目标计划和 D08 冲突值。

当前已经有 SQL 结果、文档结果、Calculation 结果和 Evidence binding，但仍缺一个可靠的声明级答案合成闭环：

~~~text
actual -> target -> formula -> calculation -> answer claim -> citation
~~~

常见状态是 SQL 成功、RAG 成功、计算节点部分成功，但最终 composer 因证据绑定或渲染规则返回 insufficient_evidence。

### 4.3 跨源查询计划还没有真正执行成多步检索

当前已经为问题生成 required_sources、evidence_requirements、query_terms，但 required_sources 主要参与候选排序和覆盖奖励。

如果某个 required source 没有词法命中，系统不会自动执行：

~~~text
针对 D09 单独补检索
针对 D08 单独补检索
针对 D11 单独补检索
~~~

因此仍会出现：

- cross-003 需要 D08、D09，实际拿到 D01、D06、D07；
- cross-004 需要 D04，SQL 失败后没有形成 D04 证据；
- cross-009 需要 D06、D08，实际主要拿到 D06；
- cross-006 需要 D05、D11，SQL 失败后没有形成两类证据。

当前系统已经有“检索计划数据结构”，但还没有完整的“缺证据补检索循环”。

还要区分两类情况：

1. SQL 先失败，cross_source 流程可能直接进入证据检查，RAG 证据不会进入最终答案。这不能简单判断为 RAG 召回失败；
2. SQL 成功、RAG 也被调用，但 required source 仍然缺失，这才是 A 线覆盖或来源计划执行问题。

### 4.4 澄清策略仍与验收槽位不一致

澄清专项仍为 2/8 = 25%，主要问题是：

- comparison_period、data_scope、year、quarter 混用；
- 期望 media_scope，实际询问 year；
- 期望 period、scope、target_metric，实际返回 quarter、scope、year；
- 期望 genre_scope，实际返回 genre_boundary；
- “某商品属于什么类型？”没有主动澄清；
- “哪些客户是高价值客户？”没有进入正确的澄清状态。

这部分属于 C 线解析和交互契约。A 线可以提供文档所需的实体和来源，但不能单独决定所有澄清槽位命名。

### 4.5 多轮会话仍未建立稳定的上下文继承

多轮会话仍为 0/5。

失败模式包括：

- 第 1 轮缺年份时没有按评测口径继承或声明默认年份；
- 第 2 轮“那达标了吗”没有继承 Rock、Q3 和上轮指标；
- 第 3 轮切换到运营规则后没有保留已确认实体；
- 澄清之后的 pending task 与 last task 不能稳定恢复；
- 会话中的 SQL、RAG、计算证据没有形成跨轮可引用状态。

当前 session memory 能保存任务对象，但还没有形成稳定的“已确认槽位、已确认来源、已确认答案事实”分层记忆。

## 五、当前优势

### 5.1 A 线核心 RAG 已达到可用水平

当前四个最能代表 A 线的专项集全部通过：

- 基础 RAG：10/10；
- 别名分类：8/8；
- 多文档：5/5；
- 多模态：5/5。

这说明 A 线已经从“检索命中不稳定”进入“基础业务检索可靠、复杂跨源仍需协同”的阶段。

### 5.2 检索延迟保持较低

文档问答、别名、多文档和多模态大多在几十毫秒级完成。当前结构化目标证据没有显著拖慢简单 RAG。

### 5.3 来源可追溯和安全边界仍在

- SQL 经过 C 只读安全校验；
- 文档 chunk 保留 doc_id、页码、section、source_uri；
- D06 结构化目标记录保留页码和来源 URI；
- unsupported 问题不会继续硬答；
- 117 个单元/集成测试全部通过。

### 5.4 方案具备阶段回退能力

A1、A2、A3 和路由修正分别提交，可以单独回退和对比，不需要一次性撤销全部修改。

## 七、结论

本轮 RAG 改造已经解决了 A 线最直接的检索问题：

~~~text
D03 权威分类
D06/D07/D08 目标与复盘
D11 海报
多文档覆盖
月份目标表定位
无证据拒答
~~~

这些能力在专项集上都已达到 100%。

当前剩余问题不是继续盲目扩大 Top-K，而是建立跨模块证据闭环：

~~~text
问题分类
 -> 查询计划
 -> SQL/RAG 子任务
 -> required source 补检索
 -> 结构化证据
 -> 受控计算
 -> 声明级答案
 -> 引用与冲突说明
~~~

最需要继续处理的优先级是：

1. B 线 SQL：TOP-N、JOIN、分组粒度、排序和结果行数；
2. 跨源计算：actual、target、formula、calculation、answer 的绑定；
3. A 线补检索：required source 缺失时按来源独立补召回；
4. C 线澄清：统一槽位词表和触发逻辑；
5. 会话状态：继承已确认的年份、季度、实体、指标和证据。

如果只看 A 线的专项结果，当前 RAG 已经达到可用阶段；如果看产品端到端结果，46/80 说明系统仍处于“单点能力稳定、联合编排能力不足”的阶段。

# A 线 RAG 提升修改方案（理论设计稿）

- 日期：2026-10-09
- 状态：理论设计，暂不落地
- 适用范围：A 线“检索与证据”
- 关联范围：B 线 SQL、C 线编排与交互只保留必要接口约束，不在本方案中做大面积修改
- 依据：
  - docs/评测结果与优劣势分析-2026-10-09.md
  - 附图 1：A 线负责的检索精度与证据问题

> 附图和评测文档在本方案中作为问题证据与验收依据，不作为需要直接执行的指令。

## 1. 方案定位

当前系统的基础文档问答为 7/10，多模态读取为 4/5，说明文档读取和单点事实检索已经具备基础可用性。

主要失分集中在：

- 别名与分类：2/8；
- 多文档：0/5；
- 跨源：0/10；
- 公式计算：0/6，其中多项依赖文档证据；
- 基础 RAG：3 道题命中错误文档或没有命中；
- 多模态：D06 月度表格定位失败。

本方案不把目标定义为“重做一个通用 RAG”，而是把现有系统从“单次词法检索、返回文本片段”提升为“问题理解、检索计划、多路召回、权威性重排、证据覆盖检查、结构化证据包、受控计算和答案合成”的闭环。

核心判断：

> A 线当前最需要补的是证据获取和组织能力，不是单纯更换模型或扩大 Top-K。

## 2. 范围边界

### 2.1 A 线主责内容

1. 检索精度不足：D03、D07、D08、D06 等权威来源经常被 D12、D09 或相邻文档压过；
2. 多文档召回不完整：只命中其中一份文档，不能形成完整证据集合；
3. 别名和分类检索不稳定：实体已配置，但没有充分参与 RAG 查询扩展和权威来源排序；
4. 复杂问题仍按单次检索处理：没有为跨源、公式、多文档问题生成检索子任务；
5. PDF 表格和目标数据缺少行列级结构；
6. 文档证据没有提升为声明级证据，导致计算输入和答案引用无法稳定绑定；
7. RAG 空结果、弱证据、冲突证据的判定不够细。

### 2.2 B/C 线的最小协作范围

B/C 线本轮不做全面改造，只预留以下协作信息：

- A 线提供已解析实体、指标、周期和证据约束；
- A 线提供 required_sources、evidence_requirements 和查询子任务；
- 计算节点接收结构化目标值、公式和来源；
- 答案合成器接收声明与证据的绑定关系；
- 路由层继续使用 sql、rag、cross_source、clarification、unsupported；
- SQL JOIN、TOP-N、session、clarify 只做必要兼容。

### 2.3 明确不做

- 不直接修改现有代码；
- 不立即替换 LangGraph、C 服务或前端接口；
- 不把所有文档改造成知识图谱；
- 不以向量检索替代现有词法检索；
- 不让大模型直接决定关键业务数值；
- 不把所有跨源问题交给自由 Agent 自主循环；
- 不使用最终准确率作为唯一验收标准。

## 3. 当前问题诊断

### 3.1 词法相关性不能表达业务权威性

现有知识索引主要依靠中文二元词、IDF 和少量文档提示。它能处理原文词汇重合，却不能稳定理解：

- 摇滚、Rock、摇滚乐之间的业务关系；
- 核心结果、经营表现、复盘结论之间的语义关系；
- D03 是分类权威来源、D12 是 FAQ 补充来源；
- Q2 和 Q3 复盘必须分别覆盖 D07 和 D08。

这解释了以下评测现象：

- “摇滚默认对应哪个 Genre？”命中 D12；
- “重金属是否并入 Metal？”命中 D09；
- “拉丁音乐对应哪个 Genre？”命中 D06；
- “三季度全音频目标完成了吗？”命中 D06，而不是 D08。

问题不是文档缺失，而是排序没有使用业务来源关系。

### 3.2 单一全局 Top-K 不保证多文档覆盖

多文档题需要的是一个最小证据集合，而不是最相似的几个 chunk。例如：

~~~text
Q2 与 Q3 复盘变化
required_sources = {D07, D08}

目标、复盘、活动衔接
required_sources = {D06, D08, D10}

分类边界与选品
required_sources = {D03, D05}
~~~

现有全局排序可能返回同一份文档的多个 chunk，造成局部相关、整体缺证。

### 3.3 复杂问题没有查询分解

跨源问题通常包含数据库事实查询和文档规则查询两种操作。例如：

~~~text
找出销售额最高的品类
 -> 找到该品类的运营建议
~~~

第二次 RAG 检索需要使用第一次 SQL 的结果。当前系统把完整问题直接交给检索器，无法稳定完成这种依赖关系。

### 3.4 文档解析没有充分保留业务结构

当前 PDF、DOCX、图片能形成可定位 chunk，但仍缺少：

- 表格标题、行标签、列标签；
- 单元格值和单位；
- 年、季度、月份；
- 指标与数值的绑定；
- 表格内部的上下文关系。

因此 D06 能被读到，但“2025 年 9 月全音频销售额和销量计划”仍无法稳定定位。

### 3.5 RAG 结果仍是文本片段，不是证据对象

下游需要知道：

~~~text
这个片段支持哪个业务声明？
它支持的是实际值、目标值、公式还是运营建议？
它适用于哪个时间范围和实体？
它是否是权威来源？
它能否参与计算？
~~~

缺少这些信息，就容易出现：

- 数值算出但没有进入最终答案；
- 目标值找到但没有和实际值配对；
- 引用了相邻文档；
- 文档命中但证据不足时统一返回 insufficient_evidence。

## 4. 设计目标

### 4.1 质量目标

| 能力 | 目标 |
|---|---|
| 单文档精确命中 | D03、D06、D07、D08 等权威来源具有稳定优先级 |
| 别名与分类 | alias 问题能扩展别名并召回分类边界来源 |
| 多文档覆盖 | 必要文档尽量全部召回，并标记缺失来源 |
| 跨源证据 | SQL 结果、文档目标、公式和建议分开取证 |
| 表格定位 | 支持季度、月份、指标、行列级证据 |
| 证据绑定 | 每个最终声明可回溯到 SQL、文档或计算来源 |
| 拒答边界 | 区分 unsupported、insufficient_evidence 和 source_conflict |

### 4.2 性能与可解释目标

- 保留本地检索的低延迟优势；
- 只有复杂问题才启动多路召回、重排和多跳检索；
- 对候选文档和 chunk 做缓存；
- 记录解析、召回、重排、证据组装耗时；
- 能解释为什么选择某文档、哪些子项缺证、每个声明由什么支撑。

## 5. 推荐总体架构

~~~mermaid
flowchart TD
    Q[用户问题] --> P[问题解析与任务分类]
    P --> QP[查询计划器]
    QP --> R1[词法精确召回]
    QP --> R2[向量语义召回]
    QP --> R3[元数据与权威来源过滤]
    QP --> R4[表格/结构化证据召回]
    R1 --> F[候选合并]
    R2 --> F
    R3 --> F
    R4 --> F
    F --> RR[业务重排与去重]
    RR --> CC[证据覆盖检查]
    CC -->|缺少必要来源| MR[补充检索/子问题检索]
    MR --> RR
    CC --> EP[结构化证据包]
    EP --> SQL[C 线 SQL 查询]
    EP --> CALC[受控计算]
    SQL --> SYN[答案合成与声明校验]
    CALC --> SYN
    EP --> SYN
    SYN --> OUT[答案、来源、限制、trace]
~~~

SQL 和计算节点在图中表示协作接口，不代表本轮修改 B/C 线内部实现。

## 6. 核心设计一：业务知识目录和来源权威层级

### 6.1 文档目录增加业务元数据

每份文档应增加：

~~~text
doc_id
doc_type
title
topics
business_metrics
entities
aliases
periods
authority_scope
related_docs
answer_types
version
effective_date
~~~

D03 可描述为：

~~~yaml
doc_id: D03
topics: [分类, 商品范围, 媒体范围]
entities: [Rock, Metal, Latin, Heavy Metal]
answer_types: [alias_mapping, classification_boundary, media_scope]
authority_scope:
  alias_mapping: primary
  classification_boundary: primary
related_docs: [D01, D05, D12]
~~~

D12 可描述为：

~~~yaml
doc_id: D12
topics: [FAQ, 默认口径]
answer_types: [definition, faq]
authority_scope:
  alias_mapping: fallback
  classification_boundary: fallback
~~~

这样“默认音乐范围”可以同时召回 D03、D01、D12，但按问题类型决定排序。

### 6.2 建立轻量来源关系

先建立以下关系，不立即引入完整图数据库：

~~~text
alias -> canonical_entity
canonical_entity -> authoritative_document
metric -> definition_document
metric -> formula_document
target -> target_table
target -> review_document
classification -> selection_rule
activity -> poster
activity -> activity_plan
~~~

例如：

~~~text
重金属
 -> Heavy Metal
 -> D03
 -> 分类边界
~~~

~~~text
销售额达成率
 -> D02 公式
 -> D06/D08 目标或复盘
 -> SQL 实际销售额
~~~

## 7. 核心设计二：混合召回

### 7.1 四路候选召回

1. 精确词法召回：文档编号、实体、年份、季度、月份、指标和公式名称；
2. 语义向量召回：同义表达、口语表达和题文表达差异；
3. 元数据召回：年份、季度、月份、主题、指标、实体、文档类型、权威级别、答案类型；
4. 结构化证据召回：PDF 表格行列、月度目标、目标值、实际值、销量、海报商品 ID。

候选集合应为：

~~~text
candidate_set =
    lexical_candidates
  ∪ dense_candidates
  ∪ metadata_candidates
  ∪ structured_candidates
~~~

向量召回提供语义覆盖，不能替代精确实体和时间条件；词法召回保证编号、ID 和业务术语不丢失。

### 7.2 业务重排

候选 chunk 的最终排序综合：

~~~text
词法相关性
+ 语义相关性
+ 实体匹配
+ 时间匹配
+ 指标匹配
+ 主题匹配
+ 文档权威性
+ 问题类型匹配
+ 对尚未覆盖证据的补足价值
~~~

权威性必须和问题类型绑定：

| 问题类型 | 首选来源 |
|---|---|
| 别名、分类边界 | D03 |
| 指标定义、公式 | D01、D02 |
| Q3 目标 | D06 |
| Q2 复盘 | D07 |
| Q3 复盘 | D08 |
| 品类运营动作 | D09 |
| 活动方案 | D10 |
| 活动海报、报名信息 | D11 |
| FAQ 和默认统计口径 | D12 |

### 7.3 多文档覆盖

复杂问题先声明文档要求：

~~~json
{
  "question_type": "multidoc",
  "required_sources": ["D07", "D08"],
  "optional_sources": ["D02"],
  "min_distinct_docs": 2
}
~~~

排序时：

- 尚未覆盖的 required_source 获得覆盖奖励；
- 某文档已占满结果后，继续选该文档的收益降低；
- required_source 缺失时进入补充检索；
- 结果状态区分 complete、partial、conflicting、empty。

例如 D07 已找到但 D08 缺失时，应标记 partial，并明确无法完成 Q2/Q3 对比。

## 8. 核心设计三：查询计划和问题分解

### 8.1 任务分类

建议至少区分：

~~~text
single_document
alias_classification
multidoc
sql_only
cross_source
document_calculation
negative
multiturn_followup
~~~

分类结果只用于生成查询计划，不直接生成答案。

### 8.2 跨源查询计划示例

~~~json
{
  "task_type": "cross_source",
  "main_question": "最高销售品类及其运营建议",
  "subtasks": [
    {
      "id": "sql_actual",
      "source": "sql",
      "purpose": "找出销售额最高的品类",
      "depends_on": []
    },
    {
      "id": "rag_policy",
      "source": "rag",
      "purpose": "查询该品类运营建议",
      "depends_on": ["sql_actual"],
      "required_sources": ["D09"]
    }
  ],
  "claims": [
    "最高销售品类",
    "该品类运营建议"
  ]
}
~~~

### 8.3 典型任务的检索顺序

别名分类：

~~~text
识别用户别名
 -> 映射标准实体
 -> 优先检索 D03
 -> 必要时补 D01/D12
 -> 输出实体和权威引用
~~~

目标差额：

~~~text
查 SQL 实际值
 -> 查 D06/D08 目标值
 -> 查 D01/D02 公式
 -> 交给受控计算
 -> 绑定 actual、target、formula 三类证据
~~~

多文档对比：

~~~text
识别时间范围
 -> 为每个季度生成独立检索子任务
 -> 每个季度至少保留一个权威来源
 -> 检查是否覆盖全部季度
 -> 再进行比较
~~~

海报商品销售：

~~~text
从 D11 提取 TrackId
 -> 将 TrackId 作为 SQL 查询条件
 -> 查询指定周期是否成交
 -> 返回海报证据和 SQL 证据
~~~

## 9. 核心设计四：表格和多模态资料的结构化索引

D06 目标表理论上应形成行列级记录：

~~~json
{
  "doc_id": "D06",
  "page": 1,
  "table_id": "q3_target",
  "row_key": "2025-09",
  "column_key": "全音频销售额计划",
  "value": 42,
  "unit": "万美元",
  "bbox": [x1, y1, x2, y2],
  "source_uri": "data/knowledge/D06_2025Q3经营目标表.pdf#table=q3_target"
}
~~~

这样可以支持：

- 2025 年 9 月销售额目标；
- 2025 年 9 月销量目标；
- Q3 三个月计划合计；
- 目标表与复盘表逐月对比。

文本 chunk 和结构化记录应并存：

~~~text
原文 chunk：用于上下文和人工查看
结构化记录：用于指标、月份、数值和计算
坐标信息：用于 PDF/图片证据定位
~~~

D11 海报 OCR 还应尽量抽取：

~~~text
活动名称
报名截止时间
商品 ID
适用品类
地区
日期
原始 bbox
~~~

## 10. 核心设计五：声明级证据包

每条证据应包含：

~~~json
{
  "evidence_id": "ev-001",
  "claim_type": "target_value",
  "claim": "Rock 2025 Q3 销售额目标为 50",
  "value": 50,
  "unit": "USD",
  "scope": {
    "year": 2025,
    "quarter": 3,
    "genre": "Rock"
  },
  "source": {
    "type": "document",
    "doc_id": "D08",
    "locator": "page=2, section=Rock"
  },
  "authority": "primary",
  "status": "verified"
}
~~~

公式题的证据包：

~~~text
actual：SQL 查询结果
target：D06 或 D08
formula：D01 或 D02
calculation：受控计算器
~~~

最终答案生成前检查：

~~~text
每个关键数字是否有来源；
每个判断是否有支撑文档；
每个公式结果是否有全部输入；
多文档题是否覆盖全部 required_sources；
冲突来源是否显式标记。
~~~

不满足时返回 insufficient_evidence；明确知道数据或能力不存在时返回 unsupported，二者不能混用。

## 11. 与 B/C 线的最小接口

给 SQL 节点：

~~~json
{
  "entities": ["Rock"],
  "time_range": "2025 Q3",
  "metric": "sales_amount",
  "query_purpose": "actual_value_for_target_comparison",
  "evidence_requirements": ["actual"]
}
~~~

给 RAG 节点：

~~~json
{
  "query": "Rock 2025 Q3 sales target",
  "required_sources": ["D06", "D08"],
  "preferred_doc": "D08",
  "answer_type": "target_value",
  "slots": {
    "year": 2025,
    "quarter": 3,
    "genre": "Rock"
  }
}
~~~

给计算节点：

~~~json
{
  "function": "attainment_rate",
  "operands": {
    "actual": "ev-sql-001",
    "target": "ev-doc-001"
  },
  "formula_ref": "D02"
}
~~~

给答案合成器：

~~~json
{
  "claims": [
    {
      "text": "Rock Q3 实际销售额为 47.52",
      "evidence_ids": ["ev-sql-001"]
    },
    {
      "text": "Rock Q3 目标为 50",
      "evidence_ids": ["ev-doc-001"]
    }
  ],
  "coverage": "complete"
}
~~~

## 12. 分阶段方案

### 阶段 A1：检索精度和来源权威

优先解决：

- D03 分类/别名；
- D06 目标；
- D07/D08 复盘；
- D12 与权威文档之间的排序；
- 多文档来源覆盖。

理论能力：

~~~text
业务文档目录
 + alias/source 映射
 + 指标/source 映射
 + 词法与语义候选合并
 + 文档权威性重排
 + 文档去重与覆盖约束
~~~

重点验证 basic_rag、alias、multidoc，以及 cross_source 中的 RAG 部分。

### 阶段 A2：结构化文档和证据包

优先解决：

- D06 月度目标；
- D07/D08 表格和复盘指标；
- 目标值、实际值、公式输入；
- D11 海报实体抽取。

理论能力：

~~~text
表格行列记录
 + OCR 业务实体
 + 结构化证据对象
 + claim-evidence 绑定
~~~

重点验证 formula、multimodal、cross_source、negative。

### 阶段 A3：多跳检索和跨源协作

优先解决：

- SQL 结果驱动 RAG；
- 文档规则驱动 SQL；
- 多文档查询计划；
- 公式计算的完整证据链；
- 冲突来源识别。

理论能力：

~~~text
查询计划
 + 依赖子任务
 + 补充检索
 + 证据覆盖检查
 + 跨源答案合成
~~~

重点验证 cross_source、multidoc、formula、multiturn。

### B/C 线的配合窗口

A1 只要求 B/C 提供元数据和接口兼容。

A2 需要计算节点能够消费结构化证据。

A3 才需要 C 线路由和 B 线状态配合多跳流程。

因此可以先提升 A 线，而不必同步重写 B/C 两条线。

## 13. 评测设计

建议增加以下指标：

| 指标 | 解释 |
|---|---|
| Recall@K | 必要文档是否被召回 |
| MRR / nDCG | 权威文档是否排在前面 |
| Required Source Coverage | 多文档问题是否覆盖必需来源 |
| Claim Coverage | 答案声明是否都有证据 |
| Citation Precision | 引用是否真正支持结论 |
| Table Cell Accuracy | 表格是否定位到正确单元格 |
| Retrieval Empty Rate | 检索为空的比例 |
| Wrong Source Rate | 命中相邻但错误文档的比例 |
| Route-conditioned Retrieval | 正确路由前提下，RAG 是否召回正确来源 |
| Evidence Conflict Rate | 证据冲突是否被识别 |
| Latency by Stage | 解析、召回、重排、证据组装各阶段耗时 |

建议按阶段分组评测：

~~~text
A1 前后：basic_rag、alias、multidoc
A2 前后：formula、multimodal
A3 前后：cross_source、multiturn
~~~

每阶段只改变对应能力，避免同时改动路由、SQL、澄清和 RAG，导致无法判断收益来源。

## 14. 方案取舍

### 方案一：只增强词法规则

优点：成本低、延迟低，适合固定题型。

缺点：同义表达覆盖有限，规则容易膨胀，多文档和跨源提升有限。

适合作为 A1 的基础，但不应作为最终方案。

### 方案二：直接切换到向量 RAG

优点：能覆盖部分语义表达。

缺点：可能丢失年份、ID、月份等精确条件，不能自然表达文档权威性，也不能单独解决多文档覆盖和跨源依赖。

不建议单独采用。

### 方案三：业务感知的混合 RAG

组成：

~~~text
词法召回
 + 向量召回
 + 元数据过滤
 + 业务权威重排
 + 多文档覆盖
 + 查询计划
 + 证据包
~~~

优点：

- 保留当前系统的低延迟和可审计特性；
- 对别名、精确编号、月份等条件更稳定；
- 可以逐步接入跨源和公式；
- 不要求立即引入复杂图谱。

缺点：

- 需要增加索引元数据和中间契约；
- 需要新的分层评测；
- A 线与 B/C 线需要约定少量接口。

**推荐方案：方案三。**

### 14.4 开源项目借鉴关系

本方案借鉴的是成熟项目中的机制组合，不建议直接整体替换当前架构：

| 项目 | 可借鉴机制 | 对当前问题的对应关系 |
|---|---|---|
| [RAGFlow](https://github.com/infiniflow/ragflow) | 结构化文档解析、模板化切分、多路召回、融合重排、Agentic Retrieval、可定位引用 | 对应 D03/D06/D07/D08 权威检索、多文档补检索和表格证据 |
| [Kotaemon](https://github.com/Cinnamon/kotaemon) | 混合检索、重排、多文档问答、问题分解、复杂引用和多模态 QA | 对应 alias、multidoc、formula、multimodal |
| [Haystack](https://github.com/deepset-ai/haystack) | 显式 pipeline、条件分支、循环、检索和生成组件化 | 对应 A 线与现有 LangGraph/B 线之间的边界和可观测流程 |
| [LlamaIndex](https://github.com/run-llama/llama_index) | 多种索引、查询引擎、结构化抽取、重排和组合查询 | 对应文本、表格、实体和结构化目标的分层索引 |
| [LightRAG](https://github.com/HKUDS/LightRAG) | 实体关系和局部/全局检索 | 可作为轻量关系索引的后续参考，不作为 A1 首要改造项 |
| [Microsoft GraphRAG](https://github.com/microsoft/graphrag) | 从非结构化文本构建知识图谱并支持多跳查询 | 只在文档关系进一步扩大后评估，当前先采用轻量来源关系 |

这些项目的官方说明可以证明相应机制的存在，但不能直接证明其在本题数据集上一定优于当前系统。因此本方案采用“借鉴机制、保留现有契约、分阶段验证”的方式。

## 15. 风险与控制

### 风险 1：只调大 Top-K，噪声增加

控制：引入 required_sources、文档覆盖、去重和业务重排，不以召回数量代替召回完整性。

### 风险 2：向量召回覆盖错误业务口径

控制：精确实体和年份优先走词法与元数据过滤；D03、D06、D07、D08 使用问题类型相关的权威级别；语义召回只提供候选。

### 风险 3：Agentic Retrieval 变成不可控自由循环

控制：查询计划使用有限任务类型，设置最大子任务数和补检索轮数，每步使用结构化输入输出，只保留工具 trace。

### 风险 4：图谱建设超过当前需求

控制：先做轻量来源关系和业务目录，只有多文档关系规模明显增加时再评估 GraphRAG。

### 风险 5：评测题口径冲突影响结论

控制：保留已修订的显式年份题；对仍有歧义的题单独标记；将路由、检索、证据和答案合成分开评分。

## 16. 暂待确认的设计决策

1. 是否允许对所有目标/复盘题默认锚定 2025 年，还是继续要求题干显式年份；
2. D03、D06、D07、D08 的权威级别和适用范围是否由 A 线正式维护；
3. 是否允许引入本地 embedding 和 reranker；
4. D06/D07/D08 是否统一抽取为结构化表格记录；
5. required_sources 由规则配置生成，还是由查询规划模型生成；
6. cross_source 最终答案由固定模板生成，还是由受控 LLM 结合证据包生成；
7. 评测是否将“文档命中正确”与“最终答案正确”分开统计。

## 17. 结论

A 线的主要改造方向不是单点替换检索算法，而是建立一条面向业务证据的 RAG 链路：

~~~text
业务知识目录
 -> 权威来源建模
 -> 混合召回
 -> 业务重排
 -> 多文档覆盖
 -> 表格和实体结构化
 -> 查询分解
 -> 声明级证据包
 -> 受控计算和答案合成
~~~

按照当前评测优先级，建议先做：

~~~text
A1：D03/D06/D07/D08 来源权威与混合检索
A2：多文档覆盖与结构化表格证据
A3：跨源查询计划与声明级证据绑定
~~~

B 线 SQL 和 C 线编排可以暂时保持现状，只需为上述证据计划和证据包预留接口。这样既能集中解决 A 线负责的问题，也能避免在当前阶段进行大面积修改。

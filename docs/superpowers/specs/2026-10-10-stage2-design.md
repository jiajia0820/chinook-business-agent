# 阶段二安排与 Codex 执行指令

编写日期：2026-10-10

适用项目：`stage2/` 内的 Chinook Business Agent

文档性质：阶段二设计、任务拆分与后续执行约束。历史基线及历史10题成绩保持原口径；当前执行口径以第21节第三次修改为准。

**第三次修改：基础 NL2SQL 扩充至15题。** 用户明确授权011–015，本轮范围是扩题、独立核实gold与完整专项live评测，不预先承诺15/15，不自动扩充其他专项，不自动进入大范围业务代码修复。

## 1. 已确认目标

阶段二分为 A、B 两段，严格按顺序推进。

- **阶段二 A：逐项修复、逐项验收。** 当前基础 NL2SQL 集必须 **15/15，100%**（第三次修改，历史10题成绩单独保留）；其他专项分别达到 **至少 70%**。每一步完成后，Codex 自行运行对应完整评测集；未达标就分析失败、改进、重新评测，直到达标。用户补充确认：API 超时等外部调用问题可以暂缓，登记后继续不受影响的步骤，后续换模型复测；暂缓不等于通过，具体规则见第 13.1 节。
- **阶段二 B：提高正确率、扩充题库。** 只有 A 段全部专项通过，并且同一代码版本完成全量验收，才进入 B 段。先针对剩余错误提高正确率，再扩充独立题库，检验泛化能力。
- 基础 NL2SQL 的 100% 门槛已由用户单独确认。它是当前15题固定基础集的验收要求，不能解释为对所有未知问题的正确率保证。

本安排覆盖现有 11 类评测集。核心是基础 NL2SQL、多表关联、公式计算与跨源问答；检索、时间理解、澄清、别名、多轮和负例是支撑这些能力的配套步骤。

执行以“完成条件”为依据，不以工作天数或改动行数作为完成依据。本文不预设 API 消耗金额，也不授权无上限并发或无意义重跑。

## 2. 方案选择与架构边界

| 方案 | 能解决什么 | 代价与不足 | 选择 |
|---|---|---|---|
| 沿用现有架构，按失败原因修复，选择性借鉴开源实现 | 可以直接定位 SQL、路由、计算和证据问题；方便与旧结果比较 | 需要逐层处理现有实现的缺口 | **采用** |
| 整体迁移到新的 SQL/RAG Agent 框架 | 可以获得另一套工具和编排方式 | 改动大，接口和评测适配成本高，不能保证本题库正确率 | 当前不采用 |
| 主要修改提示词与增加示例 | 对部分理解与生成错误有效，试验成本低 | 无法单独解决错误聚合、丢失 Top-N、公式缺失和证据错配 | 作为局部方法使用 |

保持现有职责：B 模块负责问题理解、编排、检索、计算与答案组织；C 模块负责 SQL 生成、校验和只读执行。B 不绕过 C 执行任意 SQL。

数据流：问题与会话上下文 → 结构化业务任务 → SQL/文档检索 → 按实体、期间、单位绑定证据 → 必要的受控计算 → 完整业务答案与来源。

沿用现有 `/api/v1/ask` 对外契约。内部需要增加任务字段或计算类型时，同步更新内部模型及测试；不能悄悄改变对外字段含义。优先修改 `backend/sql_module/` 与 `services/agent_api/app/`，不直接修改 `third_party/chinook_c/` 的冻结副本。

### 3.1 回答正确的定义

一道题只有同时满足以下适用条件才判为正确：

1. 回答了题目要求的全部关键内容，没有遗漏必要指标、排名、维度或解释。
2. 数值、实体、时间范围、统计口径、单位和比较对象正确。
3. 需要计算时，输入可追溯、公式正确、结果正确；答案中的数值与结构化结果一致。
4. 需要证据时，引用具体且足以支撑结论；仅命中文档编号不足以判对。
5. 应当回答、澄清、拒绝或说明证据不足的行为正确；真正需要澄清的题，正确提出澄清也算正确。
6. 不包含会改变结论的无依据内容。超时、异常、空回答、遗漏关键内容不得从分母中排除。

SQL 排名题校验排序、方向、Top-N 与并列规则；不要求排序的集合结果按业务键比较。数值容差按指标在步骤 0 固定，金额可沿用现有 0.01 容差，整数计数应精确匹配。百分号空格可归一化，但 0.9504 与 95.04% 必须按单位换算，不能粗暴删除单位后比较。

另行报告路由与接口契约通过率。若业务答案正确但路由与旧标签不同，必须核查标签是否为必要契约约束；不能直接改标签放行，也不能仅因等价执行路径不同而判业务答案错误。评分政策在修复系统前冻结并记录。

### 3.2 回归约束

- 步骤1按当前15题集达到15/15后，后续回归必须维持15/15；历史10/10成绩不改写为15题成绩。
- 已达标专项后续不得低于门槛；上一验收版本已答对的题若出现新失败，必须定位，系统退化需修复，纯外部调用异常可按第 13.1 节暂缓复测；不得用其他题的新增通过掩盖退化。
- 每个明确宣称“已修复”的问题，其对应复现题必须通过，即使专项总分已达 70% 也不能跳过。
- 同一代码版本、同一评分规则、同一数据快照下的完整结果才可用于验收；不能拼接不同轮次的最好成绩。

## 4. 执行顺序

`步骤 0 评分与基线 → 步骤 1 基础 SQL → 步骤 2 多表关联 → 步骤 3 理解与澄清 → 步骤 4 检索与文档 → 步骤 5 公式 → 步骤 6 跨源 → 步骤 7 多轮与负例 → 步骤 8 全量验收 → 阶段二 B`

每一步遵循“复现 → 定位 → 修复 → 必要回归测试 → 完整专项 live 评测 → 检查门槛 → 记录结果”的循环。前置步骤中若发现依赖后续模块的最小修复，可提前完成该依赖并注明，不能借此跳过后续专项验收。API 超时等外部调用问题暂缓后，可继续不受影响的后续实现与本地验证，不必停留在当前步骤反复调用；该步骤仍标记为待复测。

## 5. 步骤 0：校准评分器，冻结基线和证据

**解决问题**：现有评分存在误判；只有截断答案无法检查完整性；live 模式与实际模型调用成功容易混淆。

具体工作：

1. 读取代码状态、题库 manifest、数据库和知识材料指纹，记录模型、评测器版本及环境参数。保留用户现有未提交改动。
2. 审核 `scripts/run_agent_eval.py` 的结果、公式、文档、接口及多轮比较逻辑。用明确的正反例验证评分器：同值不同格式应通过；错误实体、缺失关键内容或错误期间应失败。
3. 修复已知评分问题：百分号空格导致的误判；非排序题强制按位置比较；多轮中将合理澄清一律判错；把答案里日期、编号等全部数字当作业务数值；仅检查文档 ID 而未检查回答要求；对复杂公式只取首个数字。
4. 将 `gold_answer_requirements`、必要来源断言及多轮预期行为落实到评分规则。不能通过放宽业务要求制造达标。
5. 针对旧完整响应同时保留旧评分与校准后评分，输出发生变化的 case ID、依据、差异。确认评分规则后，再用当前代码真实请求运行全量，建立新的系统基线。
6. 记录完整响应、SQL、结果行、计算输入与输出、引用定位、状态、路由、超时、重试、降级及耗时。脱敏 API 密钥。
7. 将现有临时证据采集封装整理为可指定输出目录的正式能力。旧 `tmp/local-eval/run_with_evidence.py` 会覆盖其固定目录下的响应和调用文件，不能直接反复运行覆盖历史证据。

**重点核查案例**：`cross-001` 原响应已包含 95.04% 达成率，真正缺少差额及部分证据；`basic-rag-010` 旧评分通过，但报名材料回答不完整。评分校准必须同时纠正假阴性和假阳性。

**开源借鉴**：不需要引入新评测框架。优先修复现有评分器，采用可核查的确定性断言；人工复核用于校准有争议的规则。不得把同一模型的自我评价作为唯一通过依据。

**入口**：`scripts/run_agent_eval.py`、`eval/agent/`、`eval/human/`、已有完整响应记录。

**完成条件**：评分校准说明、正反例验证结果、新旧分数对照、新的全量基线齐备。本步骤不设业务 70% 门槛，因为其产出是可信的测量工具；所有后续业务步骤必须使用冻结后的规则。若外部调用异常使新 live 基线暂时无法完成，保留已完成结果并登记待补测项，可继续评分器及系统修复；不能把历史响应重评分称为新的 live 基线。

## 6. 步骤 1：基础 NL2SQL 恢复并保持 100%

**解决问题**：查询语法合法但统计口径错误；日期过滤未约束真正参与汇总的事实行；模型超时后降级丢失 Top-N。

具体工作：

1. 复现基础 009：日期条件只放在外连接的 Invoice 条件中，未排除参与汇总的区间外 InvoiceLine；同时检查是否无依据限定为音频媒体类型。根据业务语义调整连接与过滤，验证不存在区间外金额泄漏。
2. 复现基础 010：降级后按国家名称排序且没有 Top-5 限制。使模型生成与降级都保留指标、期间、维度、排序方向和数量约束。
3. 整理结构化查询意图，避免提示词、模型输出、校验与降级各自重新猜测口径。利用 AST 对关键查询约束做检查；不能只检查是否只读、表列是否存在。
4. 对模型超时做必要定位，区分连接、响应、重试和本地超时配置问题。合理配置下的外部调用超时可以暂缓，不要求当前阶段彻底解决供应商可用性；保持有限重试、明确总截止时间。模型失败可以走已验证的受控降级，不能用不符合题意的总计替代明细。
5. 不能仅加大超时时间宣称已修复。记录实际模型成功率、降级题数、降级正确率和延迟。

**开源借鉴**：使用项目已安装的 SQLGlot 做 AST 检查；借鉴 DAIL-SQL 的结构表达和示例选择思想改善提示输入。无需替换 C 模块，无需安装 DAIL-SQL 整套运行环境。

**入口**：`backend/sql_module/generation.py`、`validation.py`、`service.py`，以及 `services/agent_api/app/integrations/sql_d12.py`。

**评测与门槛**：完整 `eval_basic_nl2sql`，当前必须 **15/15**；009、010 均需保留修复前后 SQL 和结果对照。基础题不能只满足 7/10。

## 8. 步骤 3：时间、实体、别名与澄清

**解决问题**：题目已明确却重复澄清；月份不能解析；音频范围与流派等业务实体混淆；别名表达导致路由或口径变化。

具体工作：

5. 处理“计划/目标”和“实际”的区别，避免计划问题误走实际销售 SQL。

**开源借鉴**：本阶段不强制增加解析框架。先在现有规则和类型模型内实现；仅当失败证据表明规则无法覆盖时，再对候选解析库做小范围对比，并保留引入理由。

## 9. 步骤 4：文档检索、表格提取与答案完整性

**解决问题**：只找到文档 ID，没有拿到所需字段；多文档拼接缺失；目标表、公式口径、图片资料的信息不能完整进入答案。

具体工作：

1. 检查 D01–D12 的解析结果、分块与索引。优先保留表格的行列标题、期间、实体、单位和文件定位，避免把孤立数字当成目标值。
2. 按问题分解检索需求，分别取到目标、口径、计算规则、活动要求等证据。对需要多个文档的问题检查覆盖情况。
3. 修复回答组织：例如报名问题必须回答要求的材料和责任部门，不能只输出截止时间和资格片段。

**评测与门槛**：`eval_basic_rag` 至少 **7/10**，`eval_multidoc` 至少 **4/5**，`eval_special_multimodal` 至少 **4/5**。旧评分已经通过的组也必须在校准后重测，不能直接继承旧结论。

## 10. 步骤 5：公式、输入绑定与完整计算答案

**解决问题**：查到数值但不计算；计算输入的实体、期间或单位不一致；只回答实际值，漏掉目标、差额或达成率；计算操作本身覆盖不全。

具体工作：

1. 明确每道题所需的实际值、目标值、上期值及其来源，按业务键和期间精确绑定。区别数据库实际值与文档计划值。
2. 沿用 Decimal 和受控公式注册表。现有计算器只支持差额、达成率、增长率；依据题目和业务口径补齐所需的客单价除法、月度计划求和，并同步输入模型、许可校验及结果表示。已有可复用操作优先复用。
3. 公式至少覆盖：差额 = 实际 − 目标；达成率 = 实际 / 目标 × 100%；增长率 =（本期 − 上期）/ 上期 × 100%；客单价按已确认的销售额/订单数口径；季度计划为对应月份计划求和。
4. 处理零分母、缺数、单位冲突、期间不一致以及计数的整数约束。差额或增长率可以为负，不能将合理负值裁剪为零。
5. 修复公式 006：应取月度计划 38、40、42 并计算 120，不能用实际销售额 112.86 代替。此数值仅用于评测对照，不得硬编码为系统答案。
6. 答案中展示题目要求的计算要素，结构化 `calculations` 保留公式、输入、单位、输出和来源。答案生成器不得另行心算覆盖工具结果。

**开源借鉴**：无需更换计算引擎。沿用 Python Decimal 与现有受控计算器，重点完善证据绑定及操作覆盖。禁止对文档公式直接执行 `eval/exec`。

**入口**：`tools/local_calculator.py`、`tools/models.py`、`tools/calculation_permit.py`、`evidence/binding.py`、`evidence/models.py`、`agent/graph.py`、`response/composer.py`。

**评测与门槛**：完整 `eval_special_formula` 至少 **5/6**；增加必要的算术及绑定回归测试；同步复查跨源计算相关题，但跨源整组的门槛在步骤 6 单独验收。

## 11. 步骤 6：跨源编排、冲突处理与月度对齐

**【第二次修改关联】** 用户反馈跨源最新完整评测已到 8/10；本节的原始安排继续保留，后续重点按第 20 节补齐 `cross-004`、`cross-006` 和答案证据表达，不能因已超过 70% 而跳过这两个明确缺陷。

**解决问题**：SQL 与文档任务没有同时完成；证据无法按实体和月份对齐；有计算但答案漏项；数据冲突未解释。

具体工作：

1. 在现有 LangGraph 中明确解析、SQL、检索、对齐、计算、回答各节点的输入、输出与失败状态。SQL 与检索能否并行由依赖关系决定，最终必须完成证据汇合。
2. 以实体、期间、指标、单位为键对齐数据；月度 SQL 结果要逐月绑定目标和说明，不能把整季目标复制给每个月。
3. 修复跨源 001 的真实缺口：保留已有正确的 95.04% 达成率，补齐题目要求的差额 −2.48 及必要口径证据。不能把百分号空格误判当作公式计算失败。
4. 修复跨源 009：旧实测 SQL 已有 7、8、9 月三行，重点是跨源路由、目标与冲突说明的补全；不得沿用旧截图的“只返回一行”作为当前已证实根因。
5. 按业务规则区分实际发生值、计划目标值和说明文档中的陈述。遇到冲突，展示冲突来源与采用依据；不能不加说明地取最大值、最新检索值或任意一个值。
6. 失败传播要明确：有部分结果时返回可验证的部分内容和限制，不能把缺少关键目标或证据的回答标记为完整成功。

**开源借鉴**：建议参考 LlamaIndex 的 SQL 与向量检索组合流程，以及 LangGraph 的工作流路由与状态传递。借鉴流程和边界设计，不直接安装第二套 Agent 编排系统；项目继续使用现有 LangGraph。

**入口**：`agent/graph.py`、`agent/state.py`、`evidence/binding.py`、`knowledge/index.py`、`response/composer.py`、`services/graph_ask_service.py`。

**评测与门槛**：完整 `eval_cross_source` 至少 **7/10**；公式集至少 **5/6**，基础集 **15/15**，其他已验收专项继续满足回归要求。

## 12. 步骤 7：多轮继承与负例

**解决问题**：多轮补充信息不生效；新问题继承错误条件；上一轮证据污染本轮答案；应澄清或拒绝的问题被强行回答。

具体工作：

1. 检查待澄清任务、最近任务与当前问题的合并策略。新增或更正的期间、实体、指标应覆盖对应旧值。
2. 区分追问、换题、取消与补槽；题库会话之间必须隔离，不得带入上个会话状态。
3. 计算和引用只能使用本轮有效的证据绑定；不能把旧 SQL 结果冒充新查询结果。
4. 检查负例中的不存在对象、越界请求、证据不足与不支持操作，按预期行为回答。拒绝所有问题不能提高负例以外的能力，也不能算通用修复。

**开源借鉴**：沿用 LangGraph 和现有 SessionMemory，参考状态管理方式即可；不新增另一套对话记忆框架。

**入口**：`agent/session.py`、`agent/state.py`、`agent/parsing.py`、`agent/graph.py`、`response/composer.py`。

**评测与门槛**：`eval_multiturn` 至少 **4/5 个会话**，一个会话全部必要轮次满足预期才算通过；`eval_special_negative` 至少 **4/5**。

## 13. 每一步未达标时的自动改进循环

Codex 在获得阶段执行授权后，按以下循环连续工作，不需要每次常规修复重新征求“是否继续”。

1. **看完整失败证据**：读取原问题、实际完整回答、预期要求、SQL、引用、计算与 trace。不能只看汇总分数或截断答案。
2. **分类根因**：模型/API、理解/澄清、路由、SQL 语义、检索、绑定、公式、答案组织、会话状态、评分器。区分事实与推测。
3. **选择最小有效改进**：优先解决会影响多题的共性问题，再处理局部缺陷；记录本轮要验证的假设。
4. **先做必要局部验证**：只针对有意义的错误机制补回归测试，避免重复添加与实现同构的测试。
5. **运行完整对应专项 live 评测**：调试可跑单题，验收不得使用 `--limit`、删除失败题、只挑成功样本。
6. **运行回归**：基础集 15/15；检查已通过题是否退化及已达标组门槛。
7. **输出本轮报告**：通过数、分母、失败 ID、原因、改动、真实模型调用情况、下一轮动作。
8. **未达标继续修复**：系统能力导致的未达标必须继续改进，不能以“代码已改完”或“单元测试通过”作为结束。API 超时等外部调用异常按第 13.1 节暂缓，不要求反复重试到达标。连续无改善时更换方案或重新定位，不进行无变化的重复碰运气。

API 断连、额度耗尽、凭据失效、缺少无法推断的数据等外部条件若阻止真实验收，应保存证据，继续能完成的本地工作，再明确报告待处理事项和恢复条件。不得把 offline 结果改标成 live，不得虚报已经达到门槛。

禁止将 gold SQL、标准答案、case ID 对应关系放入运行时提示词、检索材料、降级答案表或生产分支。可以针对失败机制写通用修复；少样本示例必须与正式评测样本隔离。

### 13.1 API 超时等问题的暂缓与换模型复测规则

本节根据用户 2026-10-10 的补充要求制定，适用于所有步骤，包括基础集和最终全量验收。

1. **可暂缓的范围**：合理请求与配置下的 API 超时、连接失败、限流、供应商服务不可用等外部调用问题。保留错误码、耗时、已做的有限重试和判断依据；根因未确定时标记“疑似外部问题，待复核”，不能把所有异常归咎于模型服务。
2. **仍须修复的范围**：本地请求构造、响应解析、过短截止时间等已确认的实现错误，以及模型返回后的错误 SQL、遗漏 Top-N、错误公式、证据错配与答案不完整。特别是基础 010，API 超时可暂缓，但降级丢失 Top-5 属于系统错误，仍须修复。
3. **推进方式**：登记为“外部调用问题暂缓，待换模型复测”，停止对此原因进行无变化的重复调用，继续其他问题与后续步骤。可以使用本地测试验证修复，但不能把本地验证写成真实模型验收通过。
4. **评分方式**：保留固定题库分母，分别列出通过题、系统失败题、外部调用失败题和未完成题。因外部异常未得到正确答案的题不计通过；合法降级确实答对的题可以计通过，同时记录调用异常及降级。不能删除超时题后重新计算一个“已达标”分数。
5. **记录内容**：在 `docs/stage2-progress.md` 和当轮报告中写明 case ID、模型/端点标识（不含密钥）、错误类型、已知系统问题是否已修复、待复测范围。若还有其他系统错误，单独列出，不能随超时一起搁置。
6. **后续复测**：更换模型测试是用户已提出的后续安排。实际执行时使用届时明确的可用模型与配置，记录模型变更；当前文档不虚构替代模型。先复测暂缓题及受影响专项，再在同一代码、评分规则和数据快照下，对选定模型完整运行当前全部85个评分单位。
7. **最终状态**：允许先完成系统修复并提交“待模型复测”的阶段进展；如果暂缓事项导致门槛仍未满足，A 段不能宣称全部验收完成，也不提前扩题。换模型后的成绩独立报告，不能把不同模型各自答对的题拼成一份通过结果。

## 16. 阶段二 B：更高正确率与独立扩充

**启动条件**：步骤 8 通过，并向用户提交完整验收结果。用户原话“我们再来……优化并且扩充题库”在本文按下一轮共同确定目标处理；A 段执行授权不默认包含无上限的扩题工作。

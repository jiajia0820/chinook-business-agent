# 通用回答入口设计

## 目标

让明确的一般知识问题可以由已配置的大模型直接回答，避免因为业务知识库没有对应文档而被错误拦截；同时保留企业数字和正式业务规则的严格数据边界。

第一阶段只覆盖通用知识回答，不处理项目目录问答、联网搜索、语义模型路由和分层证据策略。这些内容分别在后续阶段处理，避免一次改变太多链路。

## 用户问题边界

- “什么是非结构化数据”“有哪些非结构化数据集”进入通用回答。
- “2025 年第三季度销售额是多少”继续进入 SQL。
- “销售额口径是什么”继续进入业务文档检索。
- 带有“本项目、我们系统、数据库、公司业务”等项目或业务指向的问题不自动当成通用知识。

## 链路变化

增加 `general` 路由和 `general_knowledge` 意图。

解析阶段对没有项目或业务指向、且明显是在解释概念、列举常见类型或请求一般介绍的问题，生成通用任务。通用任务不调用 SQL、RAG 或计算器，直接进入回答阶段。

回答阶段复用现有 JSON 模型适配器，但使用单独的通用问答提示和输出校验。模型只返回面向用户的答案文本；程序不把通用回答伪装成业务文档结论，也不允许它生成 SQL 或改变数据库。

如果没有可用的大模型，返回明确的能力不可用信息，而不是伪造答案。通用回答在来源说明中标明“通用大模型知识回答”，避免用户误以为内容来自本地业务数据库。

## 保留的安全边界

- 数据库数字、公司规则和项目事实不进入通用回答路径。
- 通用回答模型没有工具调用权限。
- 模型输出限制长度并要求结构化 JSON；非法输出会被拒绝。
- 第一阶段不声称回答最新信息、项目内部事实或联网结果。

## 验证标准

1. 一般知识问题被解析为 `general`，不再要求补充 SQL 查询意图。
2. “利润是什么”可以走通用回答；“公司利润是多少”不会因为新增通用路径而绕过业务数据边界。
3. 现有销售额 SQL 和业务文档用例的路由不改变。
4. 模型返回合法 JSON 时能生成通用回答；模型缺失或输出非法时能稳定返回失败说明。

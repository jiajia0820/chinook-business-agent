# 经营分析智能体 MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 15 号前交付一个可演示的数字音乐商店经营分析智能体，能对 Chinook 进行自然语言查数，检索经营文档，在跨源问题上主动澄清并展示 SQL、文档证据和计算口径。

**Architecture:** 采用“网页端 + Agent 编排层 + 工具层 + 数据层”。Agent 负责意图识别、数据源选择、澄清和结果合并；NL2SQL、RAG、OCR 和 SQL 校验分别作为工具；Chinook 是数字事实来源，自建经营文档是规则和目标来源。先完成一条垂直闭环，再扩展到 12 份文档和完整评测集。

**Tech Stack:** Python、FastAPI、SQLite、可配置的大模型 API、JSON 配置、JSONL 评测集；前端采用 Vue 或轻量 HTML 页面；文档解析使用 PDF/DOCX 解析库，扫描 PDF 和 PNG 使用 OCR；向量检索采用一个可替换的本地索引实现。

---

## 1. 交付边界

第一版必须支持：

- Chinook 单表和多表查数。
- 指标口径、字段含义和音乐／视频范围判断。
- 单文档 RAG 问答。
- 数据库与文档联合问题。
- 信息缺失时主动澄清。
- 无数据支撑时拒绝编造并说明数据缺口。
- 在页面中展示答案、SQL、查询结果、文档来源和计算口径。

第一版暂不做：

- 模型训练或微调。
- 多智能体协作框架。
- 真实库存、成本、利润、退款、投放和播放日志。
- CAD 或工业数据接入。
- 复杂的生产级权限、并发和数据治理平台。

## 2. 文件与模块边界

当前仓库已经有 `data/chinook/Chinook.db`、`data/chinook/Chinook_Sqlite.sql` 和 `数据集与评测集方案.md`。实现阶段按以下边界新增文件，避免所有逻辑堆在一个脚本中：

| 模块 | 建议目录 | 责任 |
|---|---|---|
| 配置和口径 | `config/` | 字段字典、指标定义、实体别名、文档目录 |
| 数据库工具 | `backend/tools/sql/` | Schema 读取、SQL 执行、只读校验、结果格式化 |
| 文档工具 | `backend/tools/rag/` | 文档解析、切片、索引、检索和来源定位 |
| Agent 编排 | `backend/agent/` | 意图识别、路由、澄清、工具调用、结果合并 |
| API | `backend/api/` | 对前端暴露统一提问接口和健康检查接口 |
| 页面 | `frontend/` | 提问、澄清、答案、SQL、证据和错误状态展示 |
| 评测 | `eval/` | JSONL 题集、执行评测和结果汇总 |
| 业务文档 | `data/knowledge/` | D01—D12 原始知识材料 |

统一的回答对象先固定为：

```json
{
  "answer": "面向用户的最终回答",
  "status": "answered | clarification_required | insufficient_evidence | error",
  "sql": "实际执行的只读 SQL，可为空",
  "table_result": [],
  "documents": [],
  "metric_definition": "本次使用的指标口径",
  "trace": [],
  "clarification_question": "需要追问时的问题，可为空"
}
```

## 6. 每天的验收原则

每天结束时只看能运行的结果，不看“写了多少代码”：

- 第一个验收点：能否对一个问题查出正确数字。
- 第二个验收点：能否从一份文档中返回正确证据。
- 第三个验收点：能否将数字和文档合并成一个答案。
- 第四个验收点：条件不足时是否会澄清。
- 第五个验收点：没有数据时是否拒绝编造。
- 第六个验收点：页面是否能展示 SQL、来源和口径。

任何新功能都必须服务于这六个验收点。先把垂直闭环跑通，再扩大数据量和页面功能。

## 一、总体结论

本轮 live 全量评测 **总分 58 / 107 = 54.21%**，比上一轮（`eb13595`，54/107）**+4 题**，是本题库扩容以来的最高分。

结构上和 10-09 那版「两极分化」的格局已经明显不同：**单点能力块基本站稳，失分集中到了少数几个确定性缺陷上**。

- **已站稳（≥87%）**：基础 NL2SQL 93.3%、专项·澄清 87.5%、专项·多表关联 87.5%。其中多表关联从 10-09 的 **0/8 → 7/8**、澄清从 **2/8 → 7/8**，是两次报告之间最大的两块进步。
- **中间地带（46%–80%）**：多模态 80%、别名 53.3%、多文档 53.3%、基础文档问答 46.7%。这一带的失分高度同质：不是「答不出来」，而是**答案里少一个词、少一个页码、少一个实体标识写法**。
- **仍是 0 分的两块**：专项·公式计算 0/6、专项·无证据处理 0/5。这两块加起来 11 题，**病因各自只有一处，且都已定位到具体代码行**（第七节），是性价比最高的两档分。
- **跨源 2/10、多轮 1/5**：跨源的病根是 D08（季度复盘）在 `cross_source` 路由下**一次都没被召回**；多轮的病根与「过度澄清」同源。

核心判断：54.21% 的构成里，**真正的能力缺口只剩「跨源/公式的证据绑定」和「多轮条件继承」两块**；其余失分绝大多数是话术、页码、实体标识写法、重复 chunk_id 触发的整轮作废这类**工程性扣分**，而不是模型或检索根本做不到。

另一个必须写进结论的事实：**本卷存在显著评测噪声**。同一 head、同一模型（deepseek-flash）连跑三次得到 44 / 47 / 55，107 题里有 **21 题（19.6%）在三次之间抖动**。因此本轮 +4 的净增中，可归因于代码改动的只有 3 题（`basic-rag-007`、`multidoc-011`、`special-multimodal-004`，这三题在 deepseek 三连跑中是 0/3 稳定失败），其余属噪声带内波动。**单轮 ±4 题以内的差异不应被当作改动效果。**

## 三、分测评集详细分析

### 3.1 基础 NL2SQL —— 14/15（93.3%）✅

**考察能力**：把「2025 年第三季度音频销售额、销量、订单数和购买客户数分别是多少」这类自然语言翻译成可执行 SQL 并返回准确数值，覆盖单期汇总、品类排名、商品排名、媒体拆分、国家排名。

**通过**：001–006、008–015（14 题）。

**失败 1 题**：`basic-nl2sql-007`「2025 年第三季度音频销售额最高的三个音乐分类是什么？」路由判对了（`sql`），但整轮 `status=error`（7.17s），limitations 只留「本轮未形成数据库查询结论」，`interface_diagnostics` 为空——是 TOP-N + JOIN 执行链路上的失败，不是路由问题。

**噪声提示**：007 在 deepseek 同 head 三连跑里属抖动题（1~2/3 通过），上轮 MiMo 通过、本轮 error，**不能据此判定为回归**，需定向复跑 3 次才能定性。

### 3.2 基础文档问答 —— 7/15（46.7%）⚠️

**考察能力**：从 D01–D12 检索并回答单点事实（指标定义、时间范围、分类边界、层级规则、目标值、季度复盘结论）。

**通过**：001、002、003、005、007、008、010。

**失败 8 题，分三类**：

1. **过度澄清 5 题（本块最大失分）**：`009`、`011`、`012`、`013`、`014` 全部 0–16ms 直接返回 `clarification_required`，`route=clarification`，**连一次检索都没发起**。这些题干在业务上条件已足够，属澄清触发条件过宽。
2. **路由误判 1 题**：`015`「同一张订单里同时有音频和视频明细，算音乐销售额时应该怎么处理？」是**规则解释题**（期望 `rag` + D12 + 数值 1/2/4/5），实际走了 `sql`，答案给的是 `查询结果：mixed_order_count 0`，还带一个空的「查询口径：；」。

**根因**：澄清门槛过低（1）、路由特征缺「规则/口径解释」信号（2）、检索召回权威出处不全 + 页码定位偏移（3）。

### 3.3 专项·澄清 —— 7/8（87.5%）✅

### 3.5 专项·多表关联 —— 7/8（87.5%）✅

**考察能力**：跨多张表 JOIN 并做 TOP-N 排名/去重汇总。

**通过**：001–007。

**失败 1 题**：`special-multitable-008`「数据库中同时含音频和视频明细的订单有多少张？」→ `unsupported`，16ms，`interface_diagnostics` 明写「route: 期望 sql，实际 unsupported」。答案原文是「该全库交易任务需要无时间范围的指标契约；当前注册交易指标要求周期，未伪造日期执行」。

## 五、劣势与失分墙（按覆盖面排序）

> 49 道失分题里，超过一半集中在下面前两堵墙；而**最便宜的分在墙 3、墙 4**——各只需一处改动。

### 墙 1：跨源/公式的证据绑定未打通（覆盖面最大）

**现象**：路由判对了（`cross_source`），检索也跑了，但计算从未执行，整轮以 `insufficient_evidence` 收场，limitations 统一是「缺少同周期/范围的有效目标与公式绑定，未执行该项」。

**命中题型**：公式 001/002/004、跨源 001/002/009，共 **6 题直接失分**；并连带 cross-003/007 的 actual/target/gap 事实缺失。

**代码位置**：`graph.py:490`（目标文档硬编码 D01/D06）、`graph.py:499`（首个绑定失败即整轮 return）、`graph.py:530-537`（`required_docs` / `evidence_coverage` / `calculations` 三道门槛任一不满足即降级）。

**关键数据**：`cross_source` 路由下 **D08 召回 0 次**，而金标准有 12 处断言要求 D08。

### 墙 2：过度澄清（策略过宽，零检索直接返回）

**现象**：0–16ms 直接 `clarification_required`，`route=clarification`，**一次检索都没发起**——说明是解析层的规则命中，不是「查了但查不到」。

**命中题型**：单轮 **9 题**（`basic-rag-009/011/012/013/014`、`cross-005/008`、`multidoc-010`、`special-formula-005`），外加多轮 `session-001`（2 轮）、`session-002`（3 轮）整组失分。合计影响 **11 条记录**。

**反向问题**：`special-clarify-007` 少列 `target_metric`、`session-004` 第 1 轮该澄清却给 `insufficient_evidence`。

### 墙 3：重复 chunk_id 触发 SourceMismatch，整轮证据被清空（确定性 bug）

**现象**：`insufficient_evidence` + `documents=[]` + limitations「来源策略或本轮引用不一致，已隐藏未获接受的结构化来源」。

**命中题型**：`special-multimodal-001`、`multidoc-005`，共 2 题。

**代码位置**：`graph.py:333`/`338` 把多次检索的 `chunks` 直接拼接、**未去重**（同文件 `343` 行的 `evidence_refs` 反而用 `dict.fromkeys` 做了去重）→ `composer.py:254-258` 的 `seen` 守卫遇到重复 `chunk_id` 直接 `raise SourceMismatch()`。

**为什么值得优先**：只有 2 题，但破坏等级是「整轮作废」，且已离线复现、修法是一行去重。同一份 chunks 还会被送进模型上下文，重复片段也在白烧 token。

### 墙 4：负例拒答话术插了内部 metric key（5 题全失）

**现象**：判断分支 5/5 全对（`unsupported`），只因答案里出现 `profit`、`play_count`、`inventory`、`ad_conversion`、`employee_sales_ranking` 这些内部 key 而非中文业务词，被扣「答案缺少必要信息」。

**代码位置**：`task_policy.py:372`。

**性质**：相对 10-09 的 3/5 是**回归**，由 `9655b7d` 引入。**5 题、一处映射，是全卷性价比最高的改动。**

### 墙 5：来源页码与权威文档召回（7 题）

**现象分两支**：

- **相邻页判错 3 题**：`basic-rag-006`（D05 期望 1 得 2）、`cross-010`（D05 期望 2 得 1）、`multidoc-004`（D05 期望 1 得 3）。**全部集中在 D05**，指向 D05 的分页/切片边界与金标准不一致。
- **目标文档未召回连带 4 题**：`basic-rag-004`、`special-alias-005`（均缺 D01）、`cross-003`、`cross-007`（均缺 D08）。这不是页码算错，是文档根本没进候选集。

**潜伏风险**：D02/D03/D04/D09/D10/D12 的召回结果 `page` 字段为 null。当前金标准未对这些文档断言页码，所以**暂不扣分**；一旦题库补上页码断言，这批会立刻变成新失分点。

### 墙 6：实体标识写法不符（4 题）

**现象**：答案写「GenreId 为 5」，评分器要字面量 `Genre:5`。命中 `special-alias-002`（Genre:5）、`011`（Genre:24）、`015`（Genre:2）、`multidoc-008`（Genre:1）。

**性质**：检索、路由、数值全对，**纯输出格式契约问题**，与检索精度无关。

### 墙 7：延迟与外部模型稳定性

**现象**：单次模型调用 avg 19.65s、max 60.09s（撞死线）；75 次 attempt 里 **9 次失败（5× `MODEL_HTTP_FAILED`、4× `MODEL_TIMEOUT`）**，失败率 12%。全局 max 74.2s 出现在多轮会话。

**影响**：`multidoc-002` 跑满 60.03s 后仍证据不足；6 题触发文档合成降级（原始 trace 中 4× TimeoutError、2× ModuleError）。这不是本地编排的性能问题，是网关侧稳定性，但它直接决定了「同一份代码两次跑分能差 11 题」的噪声量级。

## 七、确定性缺陷与可复现入口

> 以下四条不依赖模型随机性，可稳定复现，行号均以**被测提交 `554ad08`** 为准（当前工作区已有未提交的路由重构，行号会漂移）。

### 1. `special-formula-003` 未捕获的 AttributeError

- **现象**：两轮均抛 `AttributeError: 'NoneType' object has no attribute 'start'`，`status`/`route` 为 null。
- **性质**：时间范围对象为 None 时直接取 `.start`，缺空值保护。属崩溃级缺陷，不是评分口径问题。
- **复现**：单题定向跑 `special-formula-003` 即可，100% 复现。

### 2. 重复 chunk_id → SourceMismatch → 整轮证据清空

- **现象**：`special-multimodal-001`、`multidoc-005` 返回 `insufficient_evidence` 且 `documents=[]`。
- **链路**：`graph.py:333`/`338` 多次检索结果拼接未去重 → `composer.py:256` `if chunk.chunk_id in seen ... raise SourceMismatch()` → documents 清空。
- **证据**：`tmp/probe_source_mismatch.txt` 已离线复现，可见 `rag.chunks` 中 `D11:B51:0:ec3463177d9f` 重复出现（multimodal-001 出现 2 次、multidoc-005 出现 3 次），而同题的 `available_source_refs` 是无重复的。
- **对照**：同文件 `graph.py:343` 的 `evidence_refs` 用 `list(dict.fromkeys(...))` 做了去重，chunks 这条路漏了。

### 3. 负例话术插入内部 metric key

- **现象**：5/5 负例题判断正确但话术含 `profit` / `play_count` / `inventory` / `ad_conversion` / `employee_sales_ranking`。
- **位置**：`task_policy.py:372`。
- **证据**：`tmp/probe_neg.txt` 列出了 5 题的完整答案原文。

### 4. `eval_manifest.json` 的 `single_turn_total` 是陈旧值

- **现象**：manifest 写 `single_turn_total: 97`，但同一份 manifest 的 `files` 字典逐项相加是 **102**（15+15+8+15+8+6+5+5+10+15），加 5 组多轮 = 107，与 `report.json` 的 `total: 107` 一致。
- **影响**：不影响本轮评分（评分器按实际题数算），但任何引用 manifest 这个字段做分母的脚本都会算错通过率。

### 模型调用侧观测（非缺陷，供容量规划）

`model-calls.jsonl` 共 113 条事件：`model_attempt` 75（66 success / 9 error）、`controlled_fallback` 36、`controlled_business_query` 2。9 次失败为 5× `MODEL_HTTP_FAILED` + 4× `MODEL_TIMEOUT`。36 次 controlled_fallback 分布在 36 个不同 request_id 上，主要是 SQL 路径在模型候选不可用时回落到受控查询计划——**这是设计内行为，且回落结果仍通过 C 只读校验**。
